## Фаза 1: Безопасность и целостность данных (P0 / Critical P1)
*Цель: устранить векторы инъекций, утечек и порчи данных.*

### 1.1. Защита от OpenSSH Option Injection через host/IP/user
- [x] **Реализовать единую валидацию SSH-параметров назначения**
  - **Файлы:** `src/ssh.rs:74, 151-152, 282`, `src/audit.rs:328-329`
  - **Контекст:** Значения host/IP или jump, начинающиеся с `-` (например `-oProxyCommand=...`), воспринимаются OpenSSH как параметры командной строки.
  - **Что сделать:**
    - Создать модуль валидации (например `src/ssh/validation.rs` или функции в `src/ssh.rs`).
    - Запретить любые значения `host`, `user`, `jump_host`, начинающиеся с `-`.
    - Добавить строгую проверку формата host (валидный hostname RFC 1123, IPv4, IPv6) и username.
    - Проверять значения во всех точках входа: connect, audit, copy-id, fzf, MCP execute.
  - **Критерий приёмки:**
    - При передаче хоста `-oProxyCommand=calc` функция возвращает явную ошибку валидации и процесс `ssh` не запускается.
    - Написаны unit-тесты на недопустимые символы и префиксы `-`.

### 1.2. MCP Fail-Closed аутентификация и безопасность эндпоинта
- [x] **Запретить выполнение команд без аутентификации по умолчанию**
  - **Файлы:** `src/mcp.rs:4-5, 68-86, 157-180, 183-240, 387-400`, `src/config.rs:35-42`
  - **Контекст:** `check_auth()` возвращает `true` при пустом токене. Повреждённый конфиг откатывается к defaults без токена.
  - **Что сделать:**
    - Для `execute-command` требовать токен аутентификации по умолчанию.
    - Ошибка чтения/десериализации конфига должна завершать старт MCP с ошибкой (fail-closed), а не тихо подставлять дефолты.
    - Разрешать запуск без токена только при явном флаге `allow_unauthenticated_execute = true`.
    - Проверять HTTP метод (POST), `Content-Type: application/json` и путь эндпоинта.
  - **Критерий приёмки:**
    - Вызов `execute-command` без токена или с неверным токеном возвращает `401 Unauthorized`.
    - Тест повреждённого конфига подтверждает отказ в старте сервера.

### 1.3. Ограничение ресурсов MCP (Body, Concurrency, Timeout, Output)
- [x] **Ввести лимиты на обработку MCP-запросов и процессов**
  - **Файлы:** `src/mcp.rs:214-233`, `src/ssh.rs:177-214`
  - **Что сделать:**
    - Ограничить размер входящего HTTP body (например, до 1 МБ) через `take(limit)` вместо бесконечного `read_to_string`.
    - Установить таймаут чтения HTTP-сокета (`set_read_timeout`).
    - Ограничить число одновременных потоков/команд (пул потоков или семафор/bounded channel).
    - Ограничить сбор stdout/stderr из SSH-команды по объёму с меткой `[TRUNCATED]`.
    - Добавить таймаут выполнения удалённой команды.
  - **Критерий приёмки:**
    - Запрос с телом >1 МБ получает `413 Payload Too Large`.
    - Зависшая удалённая команда прерывается по таймауту.

### 1.4. Атомарность операций Keyring и TOML для Credentials
- [x] **Реализовать двухфазные операции с rollback для credentials**
  - **Файлы:** `src/credentials.rs:8-56`
  - **Контекст:** Неатомарное сохранение в системный keyring и файл TOML приводит к потере паролей или зависшим секретам.
  - **Что сделать:**
    - **Add:** валидация -> запись в keyring -> сохранение TOML. При ошибке TOML -> удаление секрета из keyring.
    - **Update:** валидация ID -> бэкап старого секрета -> запись нового в keyring -> запись TOML. При ошибке TOML -> откат секрета.
    - **Delete:** сохранение TOML без записи -> удаление из keyring. При ошибке удаления из keyring логировать предупреждение пользователю.
  - **Критерий приёмки:**
    - Mock-тест: симуляция сбоя сохранения TOML не оставляет сиротских записей в keyring.
